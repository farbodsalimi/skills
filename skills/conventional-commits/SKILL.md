You write commit messages that follow the [Conventional Commits](https://www.conventionalcommits.org/) specification, then create the commit.

Your goal is a message that accurately describes the change and its intent, using the correct type and scope so that automated tooling (changelogs, version bumps) works correctly.

## Handling Input

`$ARGUMENTS` is optional context from the user — a hint about the change, a type to force, an issue number, or empty.

- If `$ARGUMENTS` names a type (e.g. "fix", "this is a feat"), prefer it unless the diff clearly contradicts it.
- If `$ARGUMENTS` contains an issue reference (e.g. `#123`), add it to the footer.
- Otherwise infer everything from the diff.

## Process

### 1. Inspect the changes

Run these in parallel:
- `git status` — see what is staged vs. unstaged vs. untracked.
- `git diff --staged` — the staged changes that will be committed.
- `git diff` — unstaged changes, for context.
- `git log --oneline -15` — learn the repo's existing commit style, types, and scopes.

**Decide what to commit:**
- If changes are already staged, commit only those. Do not `git add` more.
- If nothing is staged but there are unstaged/untracked changes, tell the user nothing is staged. Ask whether to stage all changes (`git add -A`) or let them stage first. Do not stage automatically without confirmation.
- If the working tree is clean, report that there is nothing to commit and stop.

### 2. Determine the type

Use the type that matches the primary intent of the change. Prefer the type set a repo already uses (check `git log` and any commit-lint config in the repo).

Standard types:
- `feat` — a new feature (bumps minor)
- `fix` — a bug fix (bumps patch)
- `docs` — documentation only
- `style` — formatting, whitespace, no code-behavior change
- `refactor` — code change that neither fixes a bug nor adds a feature
- `perf` — performance improvement
- `test` — adding or correcting tests
- `build` — build system or dependencies
- `ci` — CI configuration
- `chore` — maintenance, tooling, housekeeping
- `revert` — reverts a previous commit

If the diff spans multiple unrelated concerns, say so and suggest splitting into separate commits rather than forcing one message.

### 3. Determine the scope (optional)

Scope is a noun describing the section of the codebase, in parentheses after the type: `feat(parser):`. Infer it from the changed paths (e.g. a single directory, package, or module). Match the casing and naming of existing scopes in the repo. Omit scope if the change is broad or no clear scope exists.

### 4. Write the message

Format:
```
<type>(<optional scope>): <description>

<optional body>

<optional footer>
```

Rules:
- **Subject line** ≤ 50 characters, imperative mood ("add", not "added"/"adds"), lowercase after the colon, no trailing period.
- **Body** — include only when the "why" is not obvious from the subject. Explain motivation and contrast with previous behavior. Wrap at ~72 chars. Separate from subject with a blank line.
- **Breaking changes** — append `!` after the type/scope (`feat!:`) AND add a `BREAKING CHANGE: <description>` footer.
- **Footer** — reference issues (`Refs: #123`, `Closes: #123`) when provided. See footer rules below.
- Do not add advertising, emoji, or "Generated by" lines unless the repo's own history uses them.

## Specification Rules

The message MUST conform to the [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) spec. The binding rules:

**Prefix:**
- Commits MUST be prefixed with a type (a noun: `feat`, `fix`, etc.), followed by an OPTIONAL scope, an OPTIONAL `!`, and a REQUIRED terminal colon and space.
- `feat` MUST be used when the commit adds a new feature. `fix` MUST be used when the commit is a bug fix. Other types (`docs`, `refactor`, etc.) MAY be used.
- A scope, when present, MUST be a noun in parentheses: `fix(parser):`.
- A description MUST immediately follow the colon + space.

**Body:**
- A body is OPTIONAL. When present it MUST begin one blank line after the description. It is free-form and MAY span multiple newline-separated paragraphs.

**Footers:**
- One or more footers MAY appear one blank line after the body.
- Each footer MUST be a word token, then a separator of either `: ` (colon-space) or ` #` (space-hash), then a string value. Example: `Reviewed-by: Z` or `Refs #133`.
- A footer token MUST use `-` in place of whitespace, e.g. `Acked-by`. The sole exception is `BREAKING CHANGE`, which MAY be used as a token with a space.
- A footer value MAY contain spaces and newlines; a value ends when the next valid token+separator pair begins.

**Breaking changes** — MUST be indicated in at least one of two ways:
1. A `!` immediately before the `:` in the type/scope prefix (`feat(api)!: ...`). If `!` is used, the `BREAKING CHANGE:` footer MAY be omitted and the description itself describes the break.
2. A footer `BREAKING CHANGE: <description>`. The token MUST be uppercase. `BREAKING-CHANGE` is synonymous with `BREAKING CHANGE` as a footer token.

Prefer using both (`!` in the prefix AND a `BREAKING CHANGE:` footer) when the break needs explanation beyond the subject.

**Case:** All units except `BREAKING CHANGE` are case-insensitive by the spec. Still, write types in lowercase to match common tooling. `BREAKING CHANGE` / `BREAKING-CHANGE` MUST be uppercase.

### 5. Create the commit

- Show the proposed message to the user first.
- Create the commit with the staged changes. Use a `HEREDOC` so multi-line messages are passed correctly:
  ```
  git commit -m "$(cat <<'EOF'
  <type>(<scope>): <subject>

  <body>
  EOF
  )"
  ```
- Run `git status` afterward to confirm the commit succeeded.
- If the commit fails (e.g. a pre-commit hook blocks it), report the failure and the hook output. Do not use `--no-verify` to bypass hooks unless the user explicitly asks.

Do not push unless the user asks.
